# Basic Workflow

A request moves through five stages: **Intake**, **Assignment**, **Delivery**, **Review**, and **Completed**. The progress bar at the top of a request shows its current stage and status.

> **Screenshot placeholder:** Request detail page with the five-stage progress bar highlighted.

## 1. Intake

A customer submits the public TA Request Form. TA Connect creates the customer and organization records when needed, creates the request, and places it with the reception team for scoping. The customer receives a confirmation email at the email address entered on the form.

## 2. Assignment

After intake, each request gets triaged as follows:

1. A Coordinator reviews and assigns the request to a program.
2. A Program Lead reviews and assigns it to a laboratory.
3. A Lab Lead or Program Lead assigns it to an Expert.

At each level, the person reviewing the request can update the fields allowed by their role. If the request was sent to the wrong group, use the backwards action button to return it to the preceding level. The button text states where the request will go.

## 3. Delivery

The assigned Expert accepts the work by clicking **Start TA and add dates**. Enter the projected start and completion dates. The request then has the **Providing TA** status.

During delivery, authorized users can:

- Update projected and actual dates
- Update the request scope where permitted
- Add internal notes
- Upload attachments
- Review the audit history of the request

When the work is ready to close, click **Start closeout process**.

## 4. Review

The Expert completes the closeout form and submits it. Draft responses save automatically while the form is open and can also be saved when the form closes.

The Lab Lead reviews the submitted form first. The Lab Lead can approve it and send it to the program, or reject it and send it back to the Expert for more information. The Program Lead then performs the same review. Program approval marks the request completed.

> **Screenshot placeholder:** Closeout form with submit, approve, and return actions.

## 5. Completed

Completed requests appear on the **Inactive** tab. Requests that were cancelled before completion also appear there with the **Unable to Address** status. An authorized Coordinator, Program Lead, or Admin can reopen an inactive request when additional work is needed.

## \*Unable to Address

At any point in the process, a request can be cancelled by a user with the proper permission. Cancelling a request marks it as **Unable to Address** and removes all of its previous assignments.

## Work with the request list

The **Active** tab separates requests into two groups:

- **Actionable** requests are currently assigned at a level where one of your roles can act.
- **Downstream** requests have moved beyond your level but remain visible to you.

The **Inactive** tab contains **Completed** and **Unable to Address** requests.

In the requests sidebar you can use the program filter, search control, and sort menu to narrow the list. You can sort by newest, oldest, or status. Click a request card to open it. Use the left and right arrows in the request header to move through the current filtered and sorted list.

> **Screenshot placeholder:** Active request list showing Actionable and Downstream groups, filters, and sorting.

## Read and update a request

The request page contains:

- Request status and workflow progress
- Customer and organization information
- Request description, challenges, goals, effort, topics, and depth
- Projected and actual completion dates
- Notes and Attachments
- Closeout information once closeout has started
- Dated audit history of changes

Edit controls appear only for fields your role can change. Assignment, cancellation, closeout, and reopening actions also depend on the request's current owner and status.
